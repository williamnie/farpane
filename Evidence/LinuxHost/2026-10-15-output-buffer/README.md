**Linux RustDesk Host 缓冲区优化实验，2026-10-15～16**

针对 linux-host 长期保持远程连接的场景，建议采用小范围采集优化，暂不启动完整 Linux 客户端重写，也不为本次性能问题迁移到 MyGo。三个 Rust 文件的改动已使 CPU 稳定下降约 12%～15%，但内存仅有约 1% 的差异，没有达到 CPU、内存同时减半的效果。

本次比较的是同一环境编译的未修改版 A 与修改版 B2；Flutter UI、协议、认证、网络及编码参数保持一致。Mac FarPane 作为控制端，产品代码未改。实施与独立复核使用 Codex，没有在本轮实施中调用 Claude。

CPU 的 100% 表示一个逻辑核。表中为 linux-host 上 RustDesk 五个进程的合计，不含另行记录的 hbbs/hbbr。PSS 按比例分摊共享页，单位 MiB。每项取三次 120 秒样本的中位数。

| 负载 | A CPU | B2 CPU | 相对下降 | A PSS | B2 PSS |
|---|---:|---:|---:|---:|---:|
| 静态桌面 | 34.29% | 30.32% | 11.59% | 449.8 | 444.4 |
| 滚动文字 | 31.65% | 26.80% | 15.33% | 451.8 | 447.6 |
| 持续动画 | 31.42% | 26.97% | 14.16% | 452.2 | 447.7 |

三种负载中，A 的最低运行均值均高于 B2 的最高运行均值。节省几乎全部集中在 `drm-recv`：静态中位数 18.69%→14.73%，滚动 18.00%→13.12%，动画 17.96%→13.21%。接收帧率保持约 29.9 FPS，没有以降帧换取 CPU 下降。

linux-host 有 16 个逻辑 CPU，以上改动节省约 0.04～0.05 个核，相当于整机容量的约 0.25～0.30 个百分点。静态负载 RAPL `package-0` 中位数为 8.24→7.96 W；这是封装传感器读数，不是插座功率。动态负载的功率波动较大，不以它作为主要结论。

补充探针测量从 `drmtap_convert_dmabuf` 入口至本机采集 IPC 的一字节 ACK 完成，覆盖转换、额外复制与帧发布，不包含完整编码、网络及显示链路。A 捕获 599 个完整样本、B2 捕获 600 个，均使用同一探针脚本和滚动负载：

| 指标 | A | B2 |
|---|---:|---:|
| 处理段平均耗时 | 7.49 ms | 5.91 ms |
| 处理段 P95 | 8.50 ms | 6.54 ms |
| C 转换返回后至 ACK 的平均耗时 | 1.146 ms | 0.023 ms |

GPU→CPU 读回仍然存在，本次主要消除的是随后那次 Rust 整帧复制。若以后要求更大幅度降低 CPU，需另做 GPU 输出 NV12／VAAPI surface 传递的专项实验；本轮没有实现或验证该路线。内存的大头也未被本次修改覆盖，界面按需运行应单独评估。

本轮运行条件与验证范围：

- linux-host：Ubuntu 26.04.1 LTS / GNOME Wayland，Ryzen 7 8745HS / Radeon 780M，16 个逻辑 CPU；安装包为 `rustdesk-unattended-wayland 1.5.0`。
- 2560×1440、H.264 VAAPI、30 FPS 目标、相同质量与码率设置；动态测试源约 60 FPS。
- 独立 GTK/OpenGL 测试窗口，Radeon 780M 硬件渲染，生成静态、滚动、动画三种可重复画面。早期共享 Chrome 样本因干扰作废，见 `results/exclusions.json`。
- 按 AB／BA／AB 顺序运行，共 18 个有效样本，净采样 36 分钟；逐样本检查焦点、视口、进程身份、源帧率与控制端帧流。
- 两台机器时钟偏移约 37.6 秒，使用前后校准对齐日志，并去掉接收端分析窗口两端各 2 秒。
- 47 个 scrap 测试与 88 个相关 root 测试通过；1 个上游 `adwaita_hotspot_survey` 测试保持忽略。
- 独立 Codex 复核发现 C 库可能覆盖 `ENOSPC` 的边界问题，已先复现失败，再修正容量判断并通过回归。
- B2 真机探针确认 20 秒内 601 帧全部直接写入调用方缓冲区，无复制回退、无转换错误。
- 完成 1440p→1080p→1440p 临时切换，恢复原模式；对应控制端窗口持续 streaming，零解码错误、零包间断。
- 另完成 30 分钟 B2 连续连接：360 个进程采样、61 个内存/FD 采样；控制端 1796 条对齐记录均处于 streaming，解码错误、重置、参考帧丢失与包间断增量均为 0，没有零帧率样本。

30 分钟观察中，采集进程 USS 从 110.43 增至 114.16 MiB，呈阶梯变化，最后 5 分钟持平；FD 在 70～71 之间，没有累积增长。这支持基本稳定性判断，不能据此保证数天或 24 小时运行无缓慢增长。

修改面仅有三个 Rust 文件：

- `libs/scrap/src/common/drmtap_dl.rs`：可选加载 `drmtap_set_output_buffer`，旧库保留复制回退。
- `libs/scrap/src/common/drm_render.rs`：仅当回收 Vec 容量足够时借给 C；返回前清除指针；尺寸增长、线性映射与旧库走原路径，并增加三个针对性回归测试。
- `src/server/drm_capturer.rs`：从现有帧池取出 Vec 后直接转换，完成后发布；保持原有 ACK、两槽回收池与 latest-frame 语义。

没有修改 libdrmtap、依赖版本、网络协议、认证或 Flutter UI。带 padding 的部分 EGL 帧可能继续走复制路径，这是保留的性能限制。实验范围为当前 linux-host 的 DRM 被控端，不代表 Linux Viewer、其他 GPU、其他发行版或其他编码器的发布验收。
