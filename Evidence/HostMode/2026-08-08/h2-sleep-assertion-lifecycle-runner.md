# H2.1.11b ready / active / disconnected sleep-assertion lifecycle runner

- 日期：2026-08-08
- 范围：Host-ready → authenticated remote screen route → Viewer disconnect → Host-ready
- 网络：runner 不主动连接 Hermes，不修改服务端
- 密钥：未读取、未输出、未写入

## Outcome

`Scripts/run-farpane-host-sleep-assertion-lifecycle.sh` now captures one explicit three-phase Host assertion lifecycle without automating the Viewer or macOS GUI. The operator starts a telemetry-enabled FarPane Host, runs the script with its exact PID, connects the Viewer when prompted, keeps the picture visible for the active phase, then disconnects when prompted.

The runner records every assertion observation from `pmset -g assertions` by exact Host PID and type. It preserves stable `ready-before`, `active` and `ready-after` phases plus both transition windows. Default acceptance requires at least 10 seconds per stable phase; one-second checks require explicit smoke mode.

`Scripts/validate-farpane-host-sleep-assertion-lifecycle.py` binds those samples to the production schema-v7 route-stop evidence generated by the same output prefix. A lifecycle cannot pass merely because some assertion appeared in the Host process: the route must contain captured frames, accepted encoded packets, a finalized writer, a finalized non-empty transport snapshot and enough runtime to cover the active phase.

## Fail-closed gates

- `ready-before`: exactly one sample per requested second and user-idle assertion count = 0;
- `active`: exactly one sample per requested second and user-idle assertion count ≥ 1;
- `ready-after`: exactly one sample per requested second and user-idle assertion count = 0;
- every sampled phase, including transitions: display-sleep assertion = 0 and explicit system-sleep assertion = 0;
- typed assertion counts never exceed the total Host PID assertion count;
- the active assertion and post-disconnect zero state must both be observed before their timeouts;
- production route evidence must appear after disconnect and satisfy the route contract above.

The validator publishes a sanitized schema-v1 run summary by `fsync` plus hard-link no-replace. Pass and fail summaries both retain all reasons; no peer ID, connection ID, server, password, key, payload, display ID or output path enters the summary.

## Operator command

```zsh
PREFIX="$PWD/Evidence/HostMode/2026-08-08/macmini-sleep-lifecycle"
FARPANE_HOST_TELEMETRY_OUTPUT="$PREFIX.route.json" \
  /Applications/FarPane.app/Contents/MacOS/RustDeskNative

# In a second terminal, while Host is ready and Viewer is disconnected:
Scripts/run-farpane-host-sleep-assertion-lifecycle.sh \
  10 "$PREFIX" <HOST_PID>
```

The runner prints exactly when to connect and disconnect. It never starts/stops FarPane, clicks GUI, changes TCC, sends input, reads credentials or contacts Hermes itself.

## Fresh verification

1. Runner `zsh -n` and validator `py_compile` pass.
2. Controlled three-phase fixture (`ready 0 → active user-idle 1 → ready 0`) plus schema-v7 production-route contract produces `status=pass`, active minimum 1 and display peak 0.
3. A fixture with display assertion during active plus user-idle leakage after disconnect exits 1, preserves `status=fail`, and reports both distinct reasons once.
4. Missing route evidence exits 1, preserves `status=fail`, and records both the absent production route and lifecycle observation failure.
5. Reusing an existing run-output path exits 2 and leaves the original summary byte-identical.
6. One-second default acceptance is rejected with exit 2 before creating artifacts.
7. A real runner smoke against an explicitly allowed non-FarPane PID with no Viewer times out after one second, exits 1, and still preserves six-column samples, lifecycle metadata and a `status=fail` summary.

The pass fixture proves the validator contract, not a real FarPane session. The no-Viewer smoke proves orchestration/failure preservation, not Host assertion behavior.

## Boundary

The new arm64 preview must still be installed on the Mac mini and exercised with another FarPane Viewer. Only that run can prove `ready 0 → active ≥1 → disconnected 0` for the product process and current signing/TCC environment.

Sleep/wake recovery, network-switch recovery and display reconfigure remain H5. This H2 step proves assertion ownership/lifetime only; it does not prevent explicit sleep or claim recovery after sleep.
